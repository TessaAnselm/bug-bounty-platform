# Ethics Checklist

Run this before every engagement. Not optional.

## Before You Start

- [ ] Read the full program policy — not just the scope list
- [ ] Identify what is explicitly **out of scope** and note it
- [ ] Confirm you are allowed to test from your location (some programs restrict by region)
- [ ] Check if automated scanning is permitted — assume it is not unless stated
- [ ] Create dedicated test accounts — never test on real user accounts
- [ ] Note the program's preferred disclosure timeline

## During Testing

- [ ] Stay within defined scope boundaries — when in doubt, do not test
- [ ] Minimal footprint — do not generate excessive traffic or load
- [ ] Never access, read, copy, or store real user data, even if exposed
- [ ] Stop at proof of concept — do not escalate a vulnerability beyond what proves impact
- [ ] If you accidentally reach out-of-scope systems, stop immediately and disclose
- [ ] Document everything as you go — requests, responses, timestamps

## Before Reporting

- [ ] Confirm the vulnerability is reproducible
- [ ] Assess real-world impact honestly — do not overstate severity
- [ ] Remove any real user data from screenshots or logs before attaching
- [ ] Check the program's report format requirements

## Reporting and Disclosure

- [ ] Submit only through the program's official channel
- [ ] Never disclose publicly before the program confirms the fix
- [ ] Respect the program's response and triage timeline
- [ ] If you disagree with a severity assessment, respond professionally
- [ ] No pressure tactics, threats, or public shaming if a report is closed

## Legal Reminder

Testing outside of an authorized bug bounty program's scope — even with good intent — can carry legal consequences under laws like the CFAA (US), Computer Misuse Act (UK), and equivalents elsewhere. Authorization from the program is your legal protection. Scope is the boundary of that authorization.
